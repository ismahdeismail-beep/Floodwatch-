# ADR-002: Python FastAPI Microservices Backend

**Status:** Accepted

## Context

The platform has distinct engineering domains (weather, hydrology, satellite,
geospatial, AI, alerts, analytics, auth, gateway). A single monolithic backend
would couple heavy geospatial/AI workloads to lightweight REST serving, slow
deploys, and create blast-radius on every change.

## Decision

- Implement backend services in **Python 3.12 + FastAPI**, one service per domain
  under `services/*`.
- Standardize the layout: `config.py` (pydantic-settings), `main.py`, `schemas.py`
  (Pydantic), `engine.py` (domain logic), `routes.py` (APIRouter).
- Each service is containerized (Dockerfile, `python:3.12-slim`) with a `/health`
  check and documented via OpenAPI at `/docs`.
- The `api-gateway` service is the single public entry point; it routes to the
  other services and enforces auth/rate limits.
- Node.js remains an option where a service is better served by the JS ecosystem,
  but no current service requires it.

## Consequences

- Independent scaling (e.g., `ai` on GPU-capable Cloud Run, `gis` with more RAM).
- FastAPI gives automatic OpenAPI schemas, pydantic validation, and async support.
- Nine services means more operational surface — mitigated by the shared layout,
  Docker Compose for local dev, and centralized observability (Prometheus/Loki).

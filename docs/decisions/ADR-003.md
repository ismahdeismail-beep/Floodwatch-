# ADR-003: PostgreSQL + PostGIS as the Geospatial Data Store

**Status:** Accepted

## Context

Flood risk is inherently spatial: counties, communities, river networks,
floodplains, gauge locations, road/bridge assets, and alert geographies all need
spatial querying (buffers, containment, nearest-neighbor, raster alignment).
The platform also requires relational integrity (users, alerts, API keys, model
registry) and transactional guarantees.

## Decision

- Use **PostgreSQL with PostGIS** as the primary operational database.
- In production, use **Supabase** (managed Postgres with PostGIS enabled, RLS,
  auth integration, storage, and backups).
- Local development uses `postgis/postgis:16-3.4` via Docker Compose.
- Spatial workflows in the `gis` service use PostGIS queries; heavy raster work
  uses GeoPandas/Rasterio/xarray with artifacts in object storage.

## Consequences

- One store serves both relational and spatial needs — no dual-database drift.
- Supabase removes operational burden (backups, replication, point-in-time recovery).
- Large rasters stay out of Postgres (object storage); PostGIS stores vector layers
  and computed floodplain geometries.
